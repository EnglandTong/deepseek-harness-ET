# 证据与完成 2.1

## 交付类别

| 类别 | 可声明内容 | 常见最低证据 |
| --- | --- | --- |
| `Contract` | schema、类型、接口或约定存在且有效 | parser/type/schema 检查 |
| `Governance` | 权限、决定或流程状态一致 | 状态校验与决定来源 |
| `Artifact` | 生成包或文件有效 | 确定性检查与消费者验证 |
| `Runtime` | 用户或操作员行为真实可用 | 自动证据加功能证据 |
| `Mixed` | 同一 Packet 包含多类交付 | 每条验收项标明类别 |

低类别结果不得升级描述为 Runtime 或 Release 完成。

## 证据阶梯

1. `Declared`：计划、文件、代码路径或 checkbox 存在。
2. `Automatic`：聚焦测试、回归、类型、构建、lint、schema 或确定性产物检查通过。
3. `Functional`：API、CLI、浏览器、产物消费者、操作流程或目标环境行为通过。
4. `Independent`：另一个评审者用任务局部材料复现证据。

完成声明不能超过最低未满足验收项的证据等级。

## 证据质量

记录执行内容、环境、时间、退出码/结果、产物路径和重大限制。成功输出保持精简并链接原始日志；失败保留有用尾部和根因证据。

## Ready For Review

所有 Must Pass 已检查、自动和功能证据通过、回归范围适当、限制明确、对齐成立且无停止门禁时才能使用。

Standard / Full Layered 工作保持 `qa_decision: Not Reviewed`，请求独立终验。

## Accepted With Risk

只有核心结果可用，剩余问题明确、非阻塞、有负责人和时限时才能使用。缺少主流程、要求环境、安全/数据门禁或最终独立证据，不属于可带风险通过。

同一重大风险连续两次，或连续三次正式 `Accepted With Risk`，触发治理复核。

## 冲突证据

采用较弱结果：build 通过但用户流程失败、聚焦测试通过但根门禁失败、截图正确但交互失败、Developer Complete 但独立 QA 失败、诊断分片通过但原全量门禁未解决，都必须保持开放。

活动时间、文件数、文档量和校验器通过本身都不是完成证据。
